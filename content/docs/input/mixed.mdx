五笔拼音混输（方案 ID `wubi86_pinyin`）是一个**五笔优先、拼音兜底**的混合引擎：输入编码时同时匹配五笔和拼音，五笔结果排在前面，忘记五笔编码时用拼音也能打出来。适合五笔初学者或偶尔忘记编码的用户。

## 工作方式

- 输入编码时**同时匹配五笔和拼音**
- 五笔匹配结果排在前面，拼音候选作为兜底

输入示例：

```text
wq    → 你（五笔匹配）
nihao → 你好（拼音兜底）
```

## 混输方案自己没有词库 [#no-own-dict]

这是理解混输最关键的一条：**混输方案不拥有任何词库**。它的方案文件里没有 `[[dictionaries]]` 段，只声明"我由谁组成"：

```toml
[engine.mixed]
primary_schema = "wubi86"       # 主方案（码表）——五笔候选与五笔词库都来自它
secondary_schema = "pinyin"     # 辅助方案（拼音）——拼音候选与拼音词库都来自它
# 同段还有 codetable_weight_boost，见下文「五笔为何总排在前」
```

这两个字段不只决定候选来源，也决定**词库来源**：混输里出现的每一个候选，都出自这两个被引用方案的词库，混输本身只负责把两路候选融合、排序、竞争上屏。

由此得到两条实用推论：

- **要给混输加词库、开关附加词库，得去五笔方案或拼音方案上改**——混输方案里没有任何可改的词库项。改完对原方案与混输同时生效。
- 在五笔方案下造的词、导入的用户词库，切到混输立刻能用；反过来也一样。它们本就是同一份数据，不存在"同步"这回事。

### 用户数据归到哪个方案

既然词库是借来的，用户数据也随之分流。混输下产生的数据按**候选来源**记账：

| 数据 | 归属方案 |
| --- | --- |
| 用户词库、临时词库、词频（五笔候选） | 主方案 `wubi86` |
| 用户词库、临时词库、词频（拼音候选） | 拼音方案 `pinyin`（全拼与双拼共用同一份） |
| 候选调整（置顶 / 隐藏） | 混输方案**自己** |

调频与自动造词的开关也一样跟着子方案走——码表侧读全局 `[schema.codetable]`，拼音侧读 `[schema.pinyin]`，混输没有自己的一套。

<Callout type="info" title="为什么只有候选调整留在混输名下">
候选调整针对的是**融合之后的候选顺序**——"在混输里把这个候选置顶"这句话，只有在混输这个上下文里才有意义，放到纯五笔或纯拼音下并不成立。其余三类数据的归属都能由候选来源唯一确定，于是直接落到子方案。

这也是[词库页](/docs/customize/dictionaries#词库管理界面)选中混输方案时只有「候选调整」一个子标签的原因——不是功能缺失，是别的数据本就不在这里。
</Callout>

开启 `enable_english` 后混进来的英文候选归**码表侧**记账，与五笔候选同一个方案 id。

## 融合策略配置

融合策略是全局唯一配置，无方案级覆盖，集中在 `config.toml` 的 `[schema.mix]` 段。出厂默认与常用项：

```toml
[schema.mix]
show_source_hint = false           # 显示候选来源标记（码表/拼音）
min_pinyin_length = 2              # 拼音最小触发长度（0=回退 2）
pinyin_only_overflow = true        # 超码长时仅查拼音
enable_english = false             # 启用英文候选
enable_pinyin_abbrev = true        # 拼音产出简拼候选（nh → 你好）
```

| 字段 | 说明 | 出厂默认 |
| --- | --- | --- |
| `show_source_hint` | 显示候选来源标记（码表/拼音） | `false` |
| `min_pinyin_length` | 拼音最小触发长度（0 回退 2，即 1 码不查拼音） | `2` |
| `pinyin_only_overflow` | 超码长时仅查拼音 | `true` |
| `enable_english` | 启用英文候选 | `false` |
| `enable_pinyin_abbrev` | 拼音是否产出[简拼](/docs/input/pinyin#简拼)候选 | `true` |

打开 `show_source_hint` 后，候选旁会标出它来自码表还是拼音，方便初学者辨认。

关掉 `enable_pinyin_abbrev` 后混输里的拼音只认全拼，候选更干净——简拼会让几乎任何字母串都可能被解释成拼音。它只影响混输的拼音子引擎，纯拼音方案不受影响。

`[schema.mix]` 还有若干控制「码表与拼音谁赢」的拦截开关（`auto_commit_block_on_pinyin`、`block_commit_on_pinyin_word` 等），完整清单见[方案与引擎配置 · 混输](/docs/advanced/config/schema#混输schemamix)。

## 五笔为何总排在前

混输的「五笔优先」由方案文件里的 `codetable_weight_boost` 保证，与[上文](#no-own-dict)的两个成员字段同属 `[engine.mixed]` 的引擎固定参数：

```toml
[engine.mixed]
codetable_weight_boost = 10000000  # 码表精确匹配提权基线（0=回退 10_000_000）
```

<Callout type="info" title="关于 codetable_weight_boost">
这是**层间隔离**机制：把整个码表层（短语 + 用户词库 + 系统码表）压在拼音字之前，让码表编码即便与拼音冲突也稳定靠前。它是引擎固定参数，不写入用户存储，也与词频调整无关。融合策略（`enable_english`、`min_pinyin_length` 等）才在全局 `[schema.mix]` 配置。
</Callout>

## 适用人群

- 五笔初学者：主用五笔，忘码时直接打拼音过渡
- 偶尔忘记编码的五笔用户：不必切方案或触发临时拼音
